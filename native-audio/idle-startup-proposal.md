# Native application audio when the selected stream is idle

## Implemented helper v5 behavior

The minimal implementation keeps the existing Cloudflare negotiation order, `pw-cat`, lease endpoint and owner watch. One 30-second deadline starts at the claim request and ends with the first successful sample write. The recorder stays attached while the same eligible stream wakes. Only a complete FL/FR route in `init/init` with an idle source, suspended recorder and a measured empty stdout queue qualifies for extended link verification. An already verified idle route can also wait for its first frame. Other incomplete routes retain the three-second discovery budget. Once admitted, a missing, replaced or foreign link ends the attempt on observation. Each startup snapshot checks the entire selected set.

The helper keeps renewing the ten-second lease every two seconds during setup, waiting and sharing. An expired or rejected grant cancels the session. The helper rechecks the lease and the pinned route before its first sample write. It sends Cloudflare's `/ready` and the desktop launcher's success acknowledgement after that write. The owner sees waiting, stereo links ready, sharing, or session ended through the existing controls. An ended attempt requires explicit action to start another.

### Isolation limit on a shared desktop graph

PipeWire 1.6.10 `port.exclusive` limits a port to one connection at a time. It leaves the choice of peer open at initial attachment and after unlinking. WirePlumber’s target and move/reconnect rules govern its own link selection. PipeWire checks link creators’ and endpoint owners’ permissions against **nodes**, with an override for universal link permission. These mechanisms do not give an ordinary recorder a per-channel allowlist against other authorized graph managers. A transient foreign connection between snapshots can escape observation, and raw stdout has no per-buffer source identity. The implementation preserves exact snapshot checks and stops on observed violations. **Strict isolation against concurrent graph edits is unresolved.** Enforcing it would require a trusted graph-wide link admission policy. [PipeWire port exclusivity](https://github.com/PipeWire/pipewire/blob/1.6.10/src/pipewire/impl-port.c#L411-L420) · [PipeWire link permission checks](https://github.com/PipeWire/pipewire/blob/1.6.10/src/pipewire/impl-link.c#L1379-L1418) · [WirePlumber target policy](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/linking/prepare-link.lua)

During the extended wait, graph checks run every 250 ms plus the duration of the snapshot. The ordinary sharing loop checks every two seconds. A known failure cancels immediately. Remote revocation follows the existing backend detection and lease-check latency. The helper uses its local lease deadline when the backend is unreachable. The following design review also describes stronger alternatives beyond this implementation.

## Original proposal

**Decision proposed for helper v5 at `ae7802e`.** Keep one recorder attached to the selected stream through a bounded startup wait. Start the media transport only when the exact stereo route has been verified and that recorder produces a complete frame. Reserve the owner’s “Sharing audio” status for the first successful sample write. Use one absolute 30-second budget from claim through that write. A new attempt after any terminal outcome requires user action. The proposed limit bounds how long the user and recorder can wait.

## Can the existing recorder wake up?

Yes, provided the same stream, recorder and ports survive and negotiation succeeds. In PipeWire 1.6.10 a new link starts in `init`. Preparation returns early while either endpoint is internally inactive. The link subscribes to **both** nodes' activation changes and calls `pw_impl_link_prepare` on itself when either changes. In the Pulse compatibility server, uncorking can reactivate the existing stream. These paths give the same pair of links a way forward with the same recorder PID. [PipeWire link preparation](https://github.com/PipeWire/pipewire/blob/1.6.10/src/pipewire/impl-link.c#L975-L994) · [Endpoint activation listeners](https://github.com/PipeWire/pipewire/blob/1.6.10/src/pipewire/impl-link.c#L1238-L1267) · [Pulse stream activation](https://github.com/PipeWire/pipewire/blob/1.6.10/src/modules/module-protocol-pulse/stream.c#L231-L253)

WirePlumber 0.5.18 resolves a numeric `target.object` by serial, checks compatibility, and creates links between concrete port pairs. Rediscovering a target is unnecessary when these objects survive. PipeWire can defer preparation for busy ports or renegotiate formats. `pw-cat` writes raw stdout from delivered buffers. Reading stdout cannot supply the first buffer or uncork the application. [Target selection](https://github.com/PipeWire/wireplumber/blob/0.5.18/src/scripts/linking/find-defined-target.lua) · [WirePlumber port pairing](https://github.com/PipeWire/wireplumber/blob/0.5.18/modules/module-si-standard-link.c#L325-L374) · [PipeWire state checks](https://github.com/PipeWire/pipewire/blob/1.6.10/src/pipewire/impl-link.c) · [pw-cat recorder](https://github.com/PipeWire/pipewire/blob/1.6.10/src/tools/pw-cat.c)

The Spotify observation establishes that serial 103 was present, its public state was idle, the recorder was suspended, both links were in `init` at observation, and the kernel stdout queue contained zero bytes at inspection. It does not reveal the internal active flags, prove a Pulse cork, or establish what happened after the three-second cutoff. Spotify could resume the stream, replace it, or stay idle. Same-recorder recovery is an inference from upstream source. The tests below simulate those outcomes.

| Startup strategy | What it can accomplish | Cost and decision |
| --- | --- | --- |
| Wait with the existing recorder | Endpoint activation can prepare the original links. Once both exact links reach `paused` or `active`, a complete recorder frame supplies the missing evidence of data flow. | One recorder per selected stream, no gap or target reacquisition. Choose this path. A stuck graph consumes only the remaining startup budget. |
| Controlled recorder restart | A fresh recorder can trigger fresh port and format negotiation if the **same source has resumed** and the old recorder is demonstrably wedged. It cannot make an inactive application produce data. | Destroys the verified recorder identity, loses early frames and introduces a race with source replacement. The observation supplies no evidence that a restart is needed. Keep automatic restarts at zero. If revisited, allow at most one explicit retry, reap the old child and discard its pipe first, recheck the live claim and original core/node/serial, pin a fresh recorder, and repeat full verification within the original budget. A terminal session requires fresh consent and claim. |

## Integration points in v5

- The helper discovers the application before reading pairing JSON. It claims the session, opens LiveKit or Cloudflare media, then starts recorders and polls each tap separately at 50 ms intervals for up to three seconds. Cloudflare can call `/ready` during transport setup. After verification the helper starts its encoder and the desktop path prints `ready` without waiting for a successful sample write. Active checks and lease renewals share a two-second loop. [Helper startup](main.go) · [Graph verification](application.go) · [Media setup](transport.go)
- The backend requires an active screen and owner watch. Pairing codes last one minute, claimed leases ten seconds, and the LiveKit join token minted at claim lasts 30 seconds. Cloudflare renews during its setup, then relinquishes that timer. A longer graph wait needs its own uninterrupted authorization supervision. [Native sessions](../backend/internal/rooms/native.go) · [Discord revocation](../backend/internal/rooms/discord.go)
- The hosted pairing UI sees `active` heartbeats. The desktop launcher lists only running streams, waits up to 12 seconds for `ready`, and is behind 14/15-second proxy/client timeouts. The desktop UI intersects selection with its polled catalog and can start a new session on backoff. Extending the helper timeout alone would leave both UIs misleading and the desktop path prone to repeated starts. [Owner pairing](../frontend/src/NativeAudio.tsx) · [Launcher](launcher.go) · [Desktop proxy](../frontend/local-player.ts) · [Desktop UI](../frontend/src/DesktopAudio.tsx) · [Client session](../frontend/src/gameAudioSession.ts)

## One startup attempt

| State | Entry and work | Exit |
| --- | --- | --- |
| Authorizing | Require consent for this screen and exact set of application streams. Claim once. Establish the helper revocation watch, local lease deadline and graph observation before opening a recorder. Revalidate the selection after the claim. | Invalid identity, eligibility, isolation, screen or authority ends the attempt. |
| Attaching | Spawn one owned recorder per approved stream. Pin its process/client, generated name, node ID and serial. Allow up to the existing three seconds for ordinary node, port and link discovery. | Promote to the longer wait only with a complete exact idle route (both links in `init`, source idle, recorder suspended) or a complete verified pair. A transient partial graph has only the short discovery budget. |
| Waiting for application | Keep the same recorder and route. Observe activation, negotiation and removal on a single graph subscription. During negotiation keep the media gate closed. An exact FL/FR pair with each link `paused` or `active` verifies topology. Wait for a complete fresh frame from each verified recorder. Silence from an eligible stream is valid data. | Begin connecting once all selected taps meet both conditions. Missing PCM, successful heartbeats and repeated graph observations never extend the budget. |
| Connecting audio | Open one cancellable transport, capped by its own setup timeout and the remaining startup time. For deferred LiveKit joins mint a short-lived credential against the current lease at connect time. Discard startup frames during negotiation. | At bind, recheck authority and a synchronized graph for every tap. Arm the writer for fresh complete frames. The first successful local sample write enters Sharing. |
| Sharing audio | Publish only from the verified recorder generation. Supervise graph and authority independently of the reader, encoder and transport. Keep the existing active PCM stall limit of five seconds after startup. | Any invalidation or stall ends the entire attempt. |
| Stopped | Close the writer gate first, invalidate the attempt, cancel all work, close pipes and transport, kill and reap owned children, release slots, and revoke the server session. Cleanup is idempotent and bounded. | Late callbacks, renewals and catalog refreshes cannot start another attempt. |

**Identity and isolation.** Bind authorization to the owner, screen publication and helper session. Bind each selection to its PipeWire core cookie, playback node ID and object serial. Accept only a positively identified eligible local playback application with an unambiguous stereo output layout. Reject ambiguous client identity, browsers/remote mixes, monitor ports, sinks, sources, microphones, virtual and communication streams. A display name or PID alone cannot carry consent. Preserve the serial target, `node.dont-move`, `node.dont-fallback`, `node.dont-reconnect` and `stream.dont-remix`. Keep `node.linger` off. The separate diagnostic monitor mode has no transition from this lifecycle. [Eligibility and topology checks](application.go) · [WirePlumber linking policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html)

Require exactly two incoming links in total on **each** recorder. Match node identities, FL output → FL input and FR output → FR input, port directions, channel positions and port/link lifetimes. Pin those lifetimes as soon as the exact pair is identified. An unrelated link from the application to its headset is immaterial. Removal, replacement (even with reused IDs or names), extra input, crossed/duplicate link, link error, recorder exit, core disconnect or loss of a coherent graph ends the attempt immediately on observation. A transient discovery gap before binding has a different meaning from losing a bound object. Verify all taps in the same graph revision and apply one shared deadline to the set. Never silently shrink it.

**Input isolation.** The helper must have an input path whose only possible producers are the permitted endpoints from recorder creation to teardown. The target flags control WirePlumber policy. A later userspace snapshot, or even an asynchronous graph notification, cannot prevent a client with link-creation rights from injecting a buffer first. For the strict isolation requirement, use a trusted graph policy that admits only the approved port pairs into the owned recorder, and trustworthy playback-client identity. If the helper cannot establish that protection on a host, report isolation unavailable before capture. v5's browser-name filter and periodic snapshots alone cannot establish it. Implementing or qualifying this boundary is separate from changing the wait timer. [PipeWire link factory](https://github.com/PipeWire/pipewire/blob/1.6.10/src/modules/module-link-factory.c) · [PipeWire access control](https://docs.pipewire.org/page_access.html)

**Buffer boundary.** A frame notification during `init`, `running` on the source, or a nonempty stdout queue cannot open either gate. Keep at most one frame of scratch space per tap and discard data while the gate is closed. Establish a producer-side frame boundary on verification and again at bind. Admit only complete frames from the current boundary, rechecking cancellation and lease expiry at the final write. During idle with zero frames the reader sleeps. No encoding, replay, silence generation or energy threshold is needed to wait. Raw `pw-cat` stdout has no graph revision or capture timestamp, and sampling its queue length cannot flush libc or PipeWire buffers. A recorder adapter using a PipeWire process callback could discard/tag blocks at origin. The mock models this boundary explicitly. A raw-stdout implementation must demonstrate equivalent provenance and cutover before enabling this path.

## Revocation and resource limits

- One session supervisor owns the absolute startup timer, graph subscription, child-exit notifications, lease timer, and cancellation of every pending graph read, media setup or write. Consume an initial complete graph and ordered updates with a synchronization barrier before enabling media. Keep removal/error events even if a later snapshot looks identical. Bound the event queue and fail closed on overflow, out-of-order revisions or observer failure. Use the existing two-second per-read bound for snapshot operations. Avoid spawning a `pw-dump` process every 50 ms for the extended wait.
- Renew the claimed ten-second helper lease every two seconds from claim through teardown, independent of graph or transport progress. Include the granted remaining TTL in claim/renewal replies. Use a conservative monotonic expiry based on the corresponding request's **send** time. Only a current, authenticated successful reply received before the old expiry can advance it. Recheck expiry, owner watch, claim generation and revocation under the backend session lock **after** any slow Discord/screen check and before committing a renewal or media action. A denied renewal, control-channel loss or local expiry cancels immediately. No grace while a request is in flight.
- Deliver revocation to the helper over a lease-authenticated session watch from claim onward. Owner stop/watch closure, screen end and Discord loss revoke the backend session and retire any track immediately when detected. Push the terminal event to the helper and close the watch. The local lease timer bounds an undetectable network partition. A remote change necessarily has detection and delivery latency. A writer serialized with cancellation drops all subsequent work, including late setup completion. Media already handed to a transport cannot be recalled.
- Allow one startup per owner/screen and one recorder for each explicitly authorized stream (current desktop cap eight). The backend records the startup deadline at claim and also enforces it on pending sessions. Lease renewal cannot reset it. Each attempt has one media setup and zero automatic recorder restarts. Expiry at the exact deadline wins over simultaneous readiness. Close every child pipe before joining blocked readers, including additional taps. Perform best-effort server cleanup with its existing five-second cap after local capture has stopped.

## Owner UI and protocol

Carry versioned status on the authenticated owner watch, with session ID, increasing sequence, phase, remaining startup time and a small terminal reason enum. The server controls expiry and terminal status. Give the helper a separate lease-authenticated watch for revocation. Send phase updates under the lease immediately on transitions. Record the first-write acknowledgement separately from transport binding. Defer Cloudflare’s subscriber-visible `/ready` until that write. LiveKit can expose a published track during binding, so the owner UI must use the write acknowledgement. Negotiate capabilities at claim/watch, including any Worker route allowlist changes. Legacy v5 sessions retain their existing short startup behavior. Hide the spent pairing code on claim. Send status only to the bound owner. The owner may label the app from their local selection, while hosted/manual pairing can say “the selected application” without sending process metadata.

| UI state | Owner sees |
| --- | --- |
| Waiting | “Waiting for Spotify to send audio · 24 seconds left. Your screen is still sharing.” **Stop waiting** cancels just native audio. |
| Connecting | “Connecting application audio…” Keep the cancel control available. |
| First successful sample write | “Sharing application audio.” This describes local publication. |
| Deadline | “Audio sharing didn’t start within 30 seconds. Your screen is still sharing.” **Start audio again** requires explicit consent. |
| Source ended or replaced | “The selected application stream ended. Select an application again.” Clear the old selection. |
| Discord/screen revoked or lease expired | “Audio sharing stopped because authorization ended.” Re-pair only while eligible. |

For desktop starts, return an accepted/claimed acknowledgement promptly within the current HTTP timeouts. Subscribe to owner status for waiting and first publication. Support cancellation before and after acknowledgement. Keep the selected identity pinned when the running-only catalog drops it. Eligible present idle streams can be explicitly listed as idle. Merely finding one eligible app, refreshing the catalog, changing screens, or receiving a stale event must never initiate a replacement or re-pair after a terminal event. A screen change invalidates the old attempt. Display a new selection action. For manual pairing, show the same phases on helper stderr and in the owner's panel. Hiding the panel preserves the watch. Page exit, disabling audio and stopping the screen cancel it.

## Executable acceptance contract

[Mocked lifecycle tests](idle_startup_test.go) drive the v5 graph verifier with in-memory snapshots and a test-only model of the proposed supervisor. The clock, claim/renewal, frame boundaries, media callbacks, teardown and owner status consumer are simulated. Frame events carry a generation number and no samples. Run from `native-audio` with `go test -run '^TestIdleStartup' -count=1 .`. The existing [v5 diagnostic tests](graph_read_test.go) independently exercise the current three-second behavior.

When introducing runtime changes, run the same traces against the real supervisor with injected adapters. Add adapter-level tests for link admission and cutover, blocked-read cancellation and child reaping, backend revoke/renew races, ordered status across the hosted/desktop paths, and all-or-nothing multi-tap publication. Passing the reference model establishes the intended transitions. It cannot establish host policy, physical recovery on Spotify, or network delivery.
