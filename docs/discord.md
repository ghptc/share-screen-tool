# Discord voice-channel rooms

Run `./scripts/start-discord-dev` from the graphical workstation session for a local trial. It starts this project's loopback Compose stack and prints the simulated `/live` link. The ordinary player stays at `http://localhost:5173/`. Opening a channel link authenticates, checks the simulated voice channel and subscribes to existing screens. Screen capture starts when the user clicks **Start sharing** and approves the browser picker. [Local player and audio](local-player.md)

The fixture represents the Discord provider and the bot's private voice service. The application still performs OAuth code exchange, validates its cookie, queries membership, signs grants and connects to the admission-enabled LiveKit server. The fixture operator can change guild, channel, identity or Gateway availability with its private scenario API. A room URL carries an opaque reference. It does not contain an identity or credential. Start the regular local profile with `./scripts/start-local` for development without the fixture. To shut down the simulator and its Compose stack together, run `docker compose -f compose.yaml -f compose.discord-dev.yaml down`.

## Configure a private guild later

1. Create an application and bot in the Discord Developer Portal. Register the **exact** redirect URI `https://<player-host>/api/discord/callback`. Install the application in the private test guild with the `bot` and `applications.commands` scopes. Give it visibility of the test channels. Permit the members to use application commands. The bot requests the Guilds and Guild Voice States Gateway intents. It needs neither administrator permission nor access to voice audio. [Discord OAuth2](https://docs.discord.com/developers/topics/oauth2) · [Discord application commands](https://docs.discord.com/developers/interactions/application-commands)
2. Select two ordinary voice channels and, for cross-guild checks, a second test guild. Set `DISCORD_CHANNELS` to the comma-separated `guild-id/channel-id` allowlist on the bot and backend. Give both the same persistent, randomly generated `DISCORD_ROOM_KEY`. A channel keeps its link across restarts and empty media rooms. Rotating this key changes the links. Keep keys in protected, role-specific configuration files outside Git.
3. Build from this checkout. The backend image provides the `/server` and `/discord-bot` entrypoints. Start them as separate processes with the settings below. For a native private test, use `go run ./cmd/server` and `go run ./cmd/discord-bot` from `backend/` in separately configured shells. Build the pinned LiveKit image from `infrastructure/livekit/admission`. Supply a private LiveKit keypair and a reachable media configuration for the private guild. The shipped workstation Compose file uses loopback and development signing keys.
4. Serve the built frontend on the configured HTTPS origin with an SPA fallback for `/r/*`. Proxy the public `/api/discord/*` and `/api/native-audio/*` routes to Go, stripping the `/api` prefix and preserving the original Origin header. Enable WebSocket upgrades for signaling and streaming responses for the helper watch. Restrict `/internal/discord/admit` to the SFU and the bot's `/voice` listener to the backend. Keep OAuth callback queries, cookies, request bodies and Authorization headers out of access logs and analytics.
5. Join an allowed voice channel and invoke `/live`. The bot registers the command per configured guild and posts the link in the command context. Sign in with an account in that channel and confirm the Discord consent screen requests only `identify`. The desktop socket launcher is implemented for a localhost workstation. Automatic audio from a different computer visiting a hosted HTTPS player still requires a trusted launcher on that endpoint.

| Process | Configuration |
| --- | --- |
| Bot | `DISCORD_BOT_TOKEN`, `APP_ORIGIN`, `DISCORD_CHANNELS`, `DISCORD_ROOM_KEY`, `DISCORD_VOICE_KEY`, `DISCORD_VOICE_ADDR` (defaults to loopback port 8091) |
| Backend | `WHITERUN_ENV=production`, `DISCORD_MODE=discord`, `APP_ORIGIN`, `DISCORD_CHANNELS`, `DISCORD_ROOM_KEY`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_VOICE_URL`, `DISCORD_VOICE_KEY`, `DISCORD_ADMISSION_KEY`, `LIVEKIT_HTTP_URL`, `LIVEKIT_WS_URL=wss://<media-host>`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`. Leave `LOCAL_PLAYER_KEY` unset. Optionally deny specific accounts with `DISCORD_DENIED_USERS`. |
| Patched SFU | Matching private LiveKit keypair, `DISCORD_ADMISSION_URL=http://<private-backend>/internal/discord/admit`, `DISCORD_ADMISSION_KEY`. Use TLS or an equivalent protected transport for connections between hosts. |
| Development fixture | Enabled only by the simulator overlay on `http://localhost`. Its operator control key, OAuth secret, voice service key, mapping key and SFU admission key are separate. Production refuses simulator mode. |

## Access and revocation

The bot derives the opaque reference from both Discord IDs using a keyed digest. The backend independently resolves that reference. This implementation uses one authorization backend and the pinned, admission-enabled SFU. Multiple backend replicas would need shared application-session and reservation state. OAuth uses a one-use, browser-bound state value, S256 PKCE and a fixed callback. The application session is an opaque, Secure, HttpOnly, SameSite=Strict cookie with a one-hour lifetime. The five-minute OAuth transaction uses a separate Lax cookie for the redirect.

A successful join creates a fresh participant identity for the exact room. The browser authenticates its signaling socket with the application cookie. The Go proxy puts a 45-second viewer JWT in the upstream Authorization header. Viewer grants allow subscription. A separately authorized screen upgrade grants only screen video. The player waits for LiveKit’s permission update before publishing the already approved capture. The helper receives its own 30-second audio-only JWT and renewable 10-second screen lease. A helper that loses the screen or its watch is removed and stops capturing.

The bot applies ordered Gateway events and binds membership to the current stay in the channel. Leaving and immediately returning creates a new membership generation. A sequence gap, disconnect, unavailable guild or missing snapshot prevents authorization. The bot identifies again and waits for fresh guild snapshots. The heartbeat freshness limit is 65 seconds. [Discord Gateway events](https://docs.discord.com/developers/events/gateway-events)

The patched SFU checks the current role at each protected signaling admission, resume and token refresh. It checks connected participants every two seconds with a three-second authority timeout. A read-only query can retry a closed pooled connection within its deadline and must obtain a fresh response. Canceling one browser request denies that attempt while the independent checks continue for established media. The backend reconciles sessions, removes participants and tears down their helpers. Published tracks and pending reservations count toward four screens per room. An unused backend upgrade is reclaimed after 20 seconds plus reconciliation time. Retrying the same upgrade preserves its original deadline. An SFU reservation waiting for media lasts 15 seconds. A crashed sender's active track is released on participant departure after LiveKit's reconnect grace. Audience members and audio helpers use no screen slots.

**Revocation has a detection window.** A silent Gateway failure can take the heartbeat freshness interval to detect. Established media can continue during detection and the SFU check. A known departure blocks subsequent admission as soon as the authority sees it. Restarting the backend invalidates all in-memory sessions, grants and helper leases. A newly authenticated member can reuse the stable channel link.

Self-hosted LiveKit's normal token expiration governs initial admission and its server can refresh credentials. Removal alone is insufficient to invalidate signed grants. The local overlay withholds browser refresh JWTs, caps native refresh grants at 45 seconds and gates both old and refreshed credentials on current server state. Keep this policy in every SFU serving protected rooms. Room-instance rotation would require moving authorized users and active streams to a fresh physical room. It is a possible response to suspected signing-key compromise alongside key rotation and disconnecting the old room. [LiveKit tokens and revocation](https://docs.livekit.io/home/server/generating-tokens/)

## Validation

Install frontend dependencies and both Playwright browsers. From the graphical desktop session, run the isolated suite against the named physical output. It creates its own fixture credentials, starts only its own Compose project, tests both browsers and removes its test services.

```sh
DISCORD_VALIDATION=1 \
PLAYER_AUDIO_TEST_SINK=alsa_output.usb-HP__Inc_HyperX_Cloud_II_Wireless_0-00.analog-stereo \
  ./scripts/test-game-audio
```

The transport tests use the same OAuth and admission endpoints as the player. [Discord transport scenarios](../frontend/e2e/discord.spec.ts) · [Authorization regressions](../backend/internal/rooms/discord_test.go)

Local results on 22 November 2026 used Chromium 158, Firefox 159, real WebRTC transport and a single physical HyperX output. Discord accounts, voice events and the desktop video source were simulated.

| Check | Observed result |
| --- | --- |
| OAuth and admission | Invalid state, expired login/session, absent membership, wrong guild/channel and an unauthenticated copied link were denied. The receiver decoded a screen already live when it joined the correct channel. |
| Revocation | Moving the publisher removed its video and its PipeWire tap. A voice disconnect removed the viewer. The initial helper JWT and an actual SFU-refreshed JWT both passed validation before the move. Both received HTTP 403 on validation and signaling resume afterward, while still within their signed lifetimes. |
| Capacity and recovery | Four of five simultaneous upgrades succeeded. Five more attempts in the full room all returned 409. A viewer could stay and watch all four screens. Retrying all four vacant reservations preserved their original deadlines. The Firefox reservation and recovery case passed three additional consecutive runs. A fresh OAuth session rejoined using the same link after a backend restart, and the previous cookie returned 401. |
| Streaming and audio | Chromium and Firefox each passed 20 end-to-end scenarios. The separate whole-output-monitor diagnostic was skipped. The receiver measured both 500 and 1000 Hz in a single approved stereo mix, about −61 dBFS each. Five 60-second simultaneous shares each showed one remote Opus renderer per browser and zero additional loss or concealment after the first five seconds. Startup concealment ranged from zero to 651 samples. The strongest local tone across the five runs measured −47.5 dB for Alice and −61.5 dB for Bob relative to the intended remote tone. In the final run the corresponding levels were −76.9 and −83.3 dB. Doubling Alice’s remote volume changed the measured amplitude by 2.006× for Alice and 1.000× for Bob. After stop the replacement tap was gone at the 45 ms cleanup check. |
| Picture quality | Each browser received the generated 1920×1080 source, switched to 1280×720, then returned to native using one picker invocation. At the 30 FPS cap, two-second receiver samples measured 29.5 FPS / 640.0 kb/s in Chromium and 17.0 FPS / 187.4 kb/s in Firefox, both VP8 with zero reported drops or lost packets. |
| Code and build | Frontend production build and 78 unit/component tests passed. The backend and helper passed Go race tests and vet. Five native graph/meter checks passed, and the SFU reservation tests passed in the image build and in 15 consecutive race-detector runs. |

One earlier Chromium run timed out on initial page load while a separate Firefox stress suite was active. The clean sequential rerun passed in both browsers. The cause of that page-load timeout remains unconfirmed.
