# Discord voice-channel rooms

Run `./scripts/start-discord-dev` from the graphical workstation session for a local trial. It starts this project's loopback Compose stack and prints the simulated `/live` link. The ordinary player stays at `http://localhost:5173/`. Opening a channel link authenticates, checks the simulated voice channel and subscribes to existing screens. Screen capture starts when the user clicks **Start sharing** and approves the browser picker. [Local player and audio](local-player.md)

The fixture represents the Discord provider and the bot's private voice service. The application still performs OAuth code exchange, validates its cookie, queries membership, signs grants and connects to the admission-enabled LiveKit server. The fixture operator can change guild, channel, identity or Gateway availability with its private scenario API. A room URL carries an opaque reference. It does not contain an identity or credential. Start the regular local profile with `./scripts/start-local` for development without the fixture. To shut down the simulator and its Compose stack together, run `docker compose -f compose.yaml -f compose.discord-dev.yaml down`.

## Set up the private guild

The standalone private profile serves the player over HTTPS on port 8443. Its default address works on this workstation with two browser profiles. The regular player and simulator use port 5173. For two computers, set `DISCORD_PRIVATE_HOST` to a hostname both computers can resolve and `DISCORD_PRIVATE_IP` to this machine's reachable private IPv4 address. Allow those testers to reach TCP 8443, TCP 17891 and UDP 17892. Choose the hostname before registering the callback.

1. In **Developer Portal → Applications → your application → Bot**, reset any token shared in chat. Store the replacement in `DISCORD_BOT_TOKEN` in the checkout's owner-only `.env`. From **OAuth2**, copy the application's **Client Secret** to `DISCORD_CLIENT_SECRET`. Reset it if a development fixture used it. **General Information** supplies `DISCORD_CLIENT_ID` (Application ID) and `DISCORD_PUBLIC_KEY`. Leave **Interactions Endpoint URL** empty for Gateway delivery.
2. In **OAuth2 → Redirects → Add Redirect**, register **`https://localhost:8443/api/discord/callback`** for the default workstation profile and click **Save Changes**. For a private LAN hostname use `https://<private-host>:8443/api/discord/callback` exactly. The backend requests the user scope `identify` and uses the authorization code flow with PKCE. [Discord OAuth2](https://docs.discord.com/developers/topics/oauth2)
3. In **Installation**, enable **Guild Install**, choose **Discord Provided Link**, and set the **Guild Install** scopes to `bot` and `applications.commands`. Grant **View Channels** for the test context and save. Open the install link as a member with **Manage Server** and choose **Add to Server** for the private guild. In Discord **Server Settings → Integrations → your application**, allow the test roles and command channel. Give those members **Use Application Commands** there. The bot requests the standard **Guilds** and **Guild Voice States** intents in code. Leave privileged intents off. [Discord app installation](https://docs.discord.com/developers/resources/application) · [Command permissions](https://docs.discord.com/developers/interactions/application-commands) · [Gateway intents](https://docs.discord.com/developers/events/gateway)
4. Enable **User Settings → Advanced → Developer Mode** in Discord. Use **Copy Server ID** and **Copy Channel ID** on each ordinary voice channel. Set `DISCORD_CHANNELS` in `.env` to comma-separated `guild-id/voice-channel-id` pairs. Include two channels to exercise moving between them.
5. Run the following from the checkout. The preparation command reads the protected file, appends only absent private service keys, checks the bot's identity and its access to each voice channel, compares the exact redirect, and checks the OAuth client through Discord. It revokes its client-credentials test grant and reports only check results. A pre-start command registration can be pending. Run the same check after startup to confirm registration.

```sh
./scripts/prepare-discord-private --start && \
docker compose -f compose.discord-private.yaml cp player:/data/caddy/pki/authorities/local/root.crt "${XDG_RUNTIME_DIR}/whiterun-discord-test-root.crt"
```

The player uses a project-local certificate authority. Import that **public root certificate** as a website authority in each dedicated test browser profile, using the browser's Certificate Manager. For a second computer transfer the public certificate over a trusted channel. The private CA key stays in the project's TLS volume. Stop this profile with `docker compose -f compose.discord-private.yaml down`. Keeping the volume preserves the same CA for the next test. [Caddy local TLS](https://caddyserver.com/docs/caddyfile/directives/tls)

Keep `DISCORD_PRIVATE_ROOM_KEY` stable to preserve channel links across restarts. The standalone profile takes its private service credentials from this checkout's protected `.env`. Its backend, bot and SFU each receive only their own settings.

For manual pairing in this private profile, set `SSL_CERT_FILE` on the desktop helper process to the exported project root certificate. The helper validates TLS independently of the browser. The public-IP EC2 profile uses the desktop’s ordinary public trust store.

### Diagnose the origin and rotate exposed credentials

Run `./scripts/prepare-discord-private --show-origins` from the repository root. It compares the launcher's Compose configuration with the running backend and bot. It prints the known localhost origin, masks custom values and reports credential presence by name only. Raw Compose configuration, full container inspection and process environments can disclose credentials in terminal history or recordings.

The private backend and bot each declare `APP_ORIGIN: https://${DISCORD_PRIVATE_HOST:-localhost}:8443` in `compose.discord-private.yaml`. The launcher's protected `.env` supplies `DISCORD_PRIVATE_HOST`. Leaving it unset selects localhost. The workstation player and Discord simulator separately read `APP_ORIGIN`, which defaults to `http://localhost:5173`. Use that value in the checkout's `.env` for the standard workstation player. The hosted Worker uses its own configuration. [Worker pilot origins](cloudflare-private-player.md#2-prepare-the-one-origin-host)

If the bot token and private LiveKit admission key appear in output, rotate both before the next pilot use. This interrupts the private stack's active sessions.

1. In **Discord Developer Portal → the affected application → Bot → Reset Token**, reset the bot token. Enter the replacement in `DISCORD_BOT_TOKEN` using a protected editor for the checkout's owner-only `.env`. Update any other authorized consumer of that bot. Keep credentials out of command arguments and transcripts. [Discord bot setup](https://docs.discord.com/developers/quick-start/getting-started)
2. In the same file, delete the entire `DISCORD_PRIVATE_ADMISSION_KEY` assignment, including any duplicate assignments. The launcher generates a fresh 32-byte random key for a missing assignment. It passes the new value as `DISCORD_ADMISSION_KEY` to both the backend and patched LiveKit. Retain the separate room mapping key.
3. Run the commands below. The launcher validates the new credentials, then recreates the private services whose configuration changed and waits for readiness. A bare Compose restart keeps the old container environment. [Docker Compose restart](https://docs.docker.com/reference/cli/docker/compose/restart/)

```sh
./scripts/prepare-discord-private --start
./scripts/prepare-discord-private --show-origins
```

### Verify a real command and revocation

Join an allowlisted voice channel with a test account. Invoke the guild's **/live** slash command from the permitted command channel, open the link and approve **Identify yourself**. A second account in that voice channel should open the same link and see the first account's active screen. Use a signed-out profile with a copy of the link, then sign in as a member in a different voice channel. The first should encounter Discord sign-in and the second should receive a voice-channel denial. Move the publisher while watching from the second authorized profile, then have the viewer leave voice. Confirm the screen ends, both departed sessions lose access, and reopening the saved link requires current membership. Repeat after a Gateway reconnect. Record outcomes and times without recording OAuth redirects, cookies or media tokens.

The backend and bot both require `SCREEN_SHARE_ENV=production` and `DISCORD_MODE=discord` for the private profile. The bot alone receives the bot token. The backend alone receives the user OAuth client secret. The backend and patched SFU share a private media keypair and admission credential. The public entrypoint serves built player assets, protected room links, Discord and native-audio API routes, and RTC signaling. During an approved screen share, a Linux publisher can select an application in **Audio**. The HTTPS player pairs with the enrolled desktop launcher. **Pair manually** offers terminal pairing with a single-use code. [Hosted pairing and EC2 setup](ec2.md)

Private-mode readiness signs a viewer-only probe for a reserved room. It requires the SFU to call this backend with the current nonce and its service credential, and to return HTTP 403. Browser signaling and native credential exchange require the same check. Run `./scripts/test-discord-private` for the isolated HTTPS, copied-link, route and SFU checks. It uses fresh credentials, exercises the real private backend and pinned SFU, and removes its test project and CA afterward.

## Access and revocation

The bot derives the opaque reference from both Discord IDs using a keyed digest. The backend independently resolves that reference. This implementation uses one authorization backend and the pinned, admission-enabled SFU. Multiple backend replicas would need shared application-session and reservation state. OAuth uses a one-use, browser-bound state value, S256 PKCE and a fixed callback. The application session is an opaque, Secure, HttpOnly, SameSite=Strict cookie with a one-hour lifetime. The five-minute OAuth transaction uses a separate Lax cookie for the redirect.

A successful join creates a fresh participant identity for the exact room. The browser authenticates its signaling socket with the application cookie. The Go proxy puts a 45-second viewer JWT in the upstream Authorization header. Viewer grants allow subscription. A separately authorized screen upgrade grants only screen video. The player waits for LiveKit’s permission update before publishing the already approved capture. The helper receives its own 30-second audio-only JWT and renewable 10-second screen lease. A helper that loses the screen or its watch is removed and stops capturing.

The bot applies ordered Gateway events and binds membership to the current stay in the channel. Leaving and immediately returning creates a new membership generation. A sequence gap, disconnect, unavailable guild or missing snapshot prevents authorization. The bot identifies again and waits for fresh guild snapshots. The heartbeat freshness limit is 65 seconds. [Discord Gateway events](https://docs.discord.com/developers/events/gateway-events)

The patched SFU checks the current role at each protected signaling admission, resume and token refresh. It checks connected participants every two seconds with a three-second authority timeout. A read-only query can retry a closed pooled connection within its deadline and must obtain a fresh response. Canceling one browser request denies that attempt while the independent checks continue for established media. The backend reconciles sessions, removes participants and tears down their helpers. Published tracks and pending reservations count toward four screens per room. An unused backend upgrade is reclaimed after 20 seconds plus reconciliation time. Retrying the same upgrade preserves its original deadline. An SFU reservation waiting for media lasts 15 seconds. A crashed sender's active track is released on participant departure after LiveKit's reconnect grace. Audience members and audio helpers use no screen slots.

**Revocation has a detection window.** A silent Gateway failure can take the heartbeat freshness interval to detect. Established media can continue during detection and the SFU check. A known departure blocks subsequent admission as soon as the authority sees it. Restarting the backend invalidates all in-memory sessions, grants and helper leases. A newly authenticated member can reuse the stable channel link.

Self-hosted LiveKit's normal token expiration governs initial admission and its server can refresh credentials. Removal alone is insufficient to invalidate signed grants. The local overlay withholds browser refresh JWTs, caps native refresh grants at 45 seconds and gates both old and refreshed credentials on current server state. Keep this policy in every SFU serving protected rooms. Room-instance rotation would require moving authorized users and active streams to a fresh physical room. It is a possible response to suspected signing-key compromise alongside key rotation and disconnecting the old room. [LiveKit tokens and revocation](https://docs.livekit.io/home/server/generating-tokens/)

## Validation

On 22 November 2026 the private-profile smoke test passed against the built HTTPS player, production-mode Go backend and patched SFU. It checked a copied link before login, the PKCE redirect, route isolation and a matching authenticated admission denial. Changing just the backend callback key made readiness fail while liveness continued to pass. Chromium and Firefox each passed all four Discord transport scenarios with simulated identities and voice events in an isolated Compose project. The separate real Gateway check received READY with Guilds and Guild Voice States enabled.

Install frontend dependencies and both Playwright browsers. From the graphical desktop session, run the isolated suite against the named physical output. It creates its own fixture credentials, starts only its own Compose project, tests both browsers and removes its test services.

```sh
DISCORD_VALIDATION=1 \
PLAYER_AUDIO_TEST_SINK=alsa_output.usb-HP__Inc_HyperX_Cloud_II_Wireless_0-00.analog-stereo \
  ./scripts/test-game-audio
```
